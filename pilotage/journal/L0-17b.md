# L0-17b : garde de zone sur la base commune

## Établi
- Cause : le workflow `verifier.yml` donnait à la garde `pull_request.base.sha`, sommet de la cible figé à l'ouverture de la PR, et au différentiel eslint/tsc un worktree sur ce même commit. Dès qu'une autre session fusionnait, ses fichiers apparaissaient comme ceux de la PR.

## Fait
- `verifier.yml` (jobs `zone` et `differentiel`) : checkout de la tête réelle de la PR (`pull_request.head.sha`, pas le commit de fusion) ; base = `git merge-base HEAD origin/<branche cible>` (cible à jour grâce à `fetch-depth: 0`). Sur un push vers master, la base reste `github.event.before`. Le job `zone` passe aussi `--cible`.
- `zone-interdite.mjs` : fonction `baseCommune()` et option `--cible <ref>` (prioritaire sur `--base`, qui reste valable). Aucun contrôle retiré, aucune zone élargie.
- `tests/outils/garde-zone-base.test.ts` : dépôt git temporaire, deux cas des critères.

## Critères
1. Tenu : fichier de zone arrivé sur la cible après la création de la branche, non refusé (test).
2. Tenu : fichier de zone modifié par la branche, refusé (test).
3. Tenu : seuls les `ref:` de checkout et le calcul de la base changent ; les autres étapes et jobs (règles de fer, tests, build) sont identiques.
4. Tenu : aucun secret, aucun nom de personne.

## Limite
- Le job `tests` garde `base.sha...HEAD` (hors périmètre de la fiche).
- La garde lancée depuis la base ignore `--cible` tant que cette PR n'est pas fusionnée ; `--base` reçoit donc aussi la base commune calculée par git.
